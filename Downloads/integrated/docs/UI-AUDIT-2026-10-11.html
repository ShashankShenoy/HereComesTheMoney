P2 · 1

Customer Privacy & consent starts with an unauthorized purpose catalog

Reproduce
Sign in as customer or customer2 → Privacy & consent. The initial GET /privacy/purposes returns HTTP 403; manually run “List processing-purpose versions” to see the permission error.
Observed impact
The initial failure is swallowed and shown as “No result to display.” Customers cannot discover valid purposes through this screen, although their consent-history read works.
Source
frontend/banking.js:82,334–350 includes purpose-catalog reads for customers and chooses it as the initial operation. PurposeController.java:31 requires PRIVACY_PURPOSE_VIEW; the retail customer lacks that permission.
Suggested correction
Expose a customer-safe catalog of approved purposes, or select an authorized consent workflow and show loading failures explicitly.

P2 · 2

Staff operation menus expose customer-only workflows

Reproduce
Sign in as admin or checker → Accounts → My fixed deposits → Refresh (HTTP 409). Loans → Loans My Applications · View → Refresh (HTTP 403).
Observed impact
Valid staff accounts encounter actions that cannot work in their workspace. The generic menu also includes customer self-service endpoints in staff catalogs.
Source
frontend/banking.js:334 filters customer workflows when the actor is a customer, but does not exclude customer-only paths for employees.
Suggested correction
Filter operations by actor type and permission, preserving employee inquiries that accept an explicit customer/account.

P2 · 3

Checker collections inquiry is advertised without the required permission

Reproduce
Sign in as checker → Loans → Review overdue installments → Refresh. GET /loans/collections returns HTTP 403.
Observed impact
The checker’s read menu offers a nonfunctional inquiry.
Source
frontend/banking.js:334 permits all GET operations for checkers. LoanServicingController.java:95 requires LOAN_SERVICE, which the checker does not hold.
Suggested correction
Remove this action for unauthorized roles, or define a dedicated read permission if checkers are meant to review collections.

P2 · 4

Mobile account tables hide primary actions beyond the viewport

Reproduce
Use a 390 × 844 viewport → My accounts. Details, nominees, closure, and account/deposit opening buttons begin outside the visible table area and require horizontal swiping.
Observed impact
Account rows become unusually tall, with large blank areas and no prominent horizontal-scroll cue. At the measured state, the 316px table container held a 547px table with 255px rows; other tables were 527–687px wide.
Source
Generic table columns keep the Actions column at the right; action wrapping determines the entire row height. The document itself does not overflow.
Suggested correction
Use stacked account cards or responsive action rows, and make any retained table scrolling discoverable.

Hindi and Kannada leave new customer UI copy in English

Reproduce
Change the logged-in language to हिन्दी or ಕನ್ನಡ. Language selection persists and some labels translate, but Home, My accounts, My loans, the welcome headline, descriptions, and many quick actions remain English.

Translate the new navigation labels, hero copy, quick actions, and customer descriptions; verify mixed dynamic labels.

Limits and evidence

The audit used current frontend source and compiled backend classes in a separate local-profile instance with an in-memory H2 database. Maven confirmed the backend classes were up to date. No Oracle data was modified, and no database migration was run. This validates the local application and synthetic workflows; it does not certify the running Oracle deployment or real payment rails.

Every operation form was inspected, but each maintenance endpoint was not submitted with a complete end-to-end business fixture. Teller, treasury, ledger and other governed workflows received screen/form/read coverage plus backend regression coverage. MFA enrollment/password changes and all approval variants were not manually exercised. Audit filter controls rendered, but every filter combination was not manually submitted.

The assistant’s panel and disabled unconfigured state were checked on mobile. A model provider was not configured in this isolated instance, so live chat answers and AI-mediated operations were not exercised. Currency conversion had no current approved comparison pair in the local seed.

The initial test harness used short language codes and had some asynchronous dialog/page refresh timing issues. These were corrected or rechecked; only reproducible application findings appear above. Normalized results are in verified journeys; raw screenshot and form data are in tab sweep, operations, ledger operations and mobile/language measurements.
