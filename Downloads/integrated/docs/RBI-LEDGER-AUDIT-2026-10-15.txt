CONFIRMED FAILURES

1. HIGH - Customer position does not reconcile with the immutable ledger.
   Account ID: 6. Stored posted balance: INR 500,000.00.
   Ledger-derived balance: INR 0.00. Difference: INR 500,000.00.
   Its two posting lines net to zero. The mismatch existed before this audit
   and remains unchanged afterwards.
   Reproduced in M05_V_ACCOUNT_POSITION_RECON, GET /api/v1/reconciliation/positions
   and Transactions & ledger > Operations > List account position exceptions.
   Impact: period-close approval is blocked with RECONCILIATION_OPEN. A rollback
   Oracle test verified this behavior with a distinct checker. The close stays
   pending. No balance or opening-funding repair was attempted.

2. HIGH - Creating treasury work items fails before the approval workflow begins.
   POST /api/v1/treasury/work-items with a valid RECONCILIATION / RESERVE_ACCOUNT
   request returns HTTP 409 DATA_CONFLICT.
   Oracle service test: ORA-01400, cannot insert NULL into
   M07_TREASURY_WORK_ITEM.STATUS.
   TreasuryRepository.insertWorkItem uses SimpleJdbcInsert without restricting
   inserted columns. Defaulted columns receive explicit nulls.
   Impact: new treasury reconciliation/funding work cannot reach maker/checker
   review through the normal creation flow.
   An explicitly inserted rollback fixture separately verified self-approval
   rejection, stale-version rejection and successful independent-checker decision.
   The failed HTTP creation left no QA work item behind.

3. MEDIUM - The journal balance-control inquiry hides its result from staff.
   GET /api/v1/journals/{journalId}/control returns HTTP 200 with only journalId,
   without IS_BALANCED, DEBIT_TOTAL, CREDIT_TOTAL, LINE_COUNT or difference.
   Reproduced for eight existing reserve journals with both admin and checker1:
   16 failing API assertions, representing one underlying problem.
   Reproduced in Transactions & ledger > Operations > Get journal balance control
   with journal 20: the screen displays only JOURNAL ID 20.
   TransactionPrivacyAdvice applies account-holder visibility to this endpoint;
   internal GL journals with no customer posting lines always become ID-only.
   The separate GL account ledger and /banking/journals/{id} detail view work.
   Customer ID-only masking was checked and remains effective.
